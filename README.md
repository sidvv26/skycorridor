# SkyCorridor

A micro-airspace navigation platform prototype:

`[User selects a sky corridor] → [App fetches live wind vectors] → [Telemetry engine calculates crab angle & battery drain]`

"if the map doesn't load data in the first few seconds, give it ~30-60 seconds — the free backend is waking up."

## Structure

- `server/` — Express + TypeScript API
  - `src/data/corridors.ts` — predefined 3D linear flight corridors (start/end/altitude)
  - `src/services/windService.ts` — live wind vectors from [Open-Meteo](https://open-meteo.com/) (no API key required), linearly interpolated between the two altitude bands (10/80/120/180 m) enclosing the corridor's altitude
  - `src/engine/telemetry.ts` — the telemetry engine: wind-triangle crab angle / heading / ground speed, a simplified quadratic-drag power model for battery drain, pilot safety warnings (`assessWarnings`), a heading-relative aerodynamic decomposition (`computeAerodynamicForces` — headwind/crosswind the airframe itself feels, distinct from the course-relative crosswind the drag model above uses internally), and a flat "battery consumption multiplier" (`computePowerMultiplier` = `1.0 + 0.02·|headwind| + 0.03·|crosswind|`) plus `reservePercent` for dashboard display
  - `src/engine/telemetry.test.ts` — unit tests (vitest) covering headwind/tailwind/crosswind cases and every warning condition
  - `GET /api/telemetry/:corridorId` — telemetry for a predefined corridor; `POST /api/telemetry/custom` — telemetry for an arbitrary corridor payload (used by user-drawn corridors, which the server never stores)
  - `src/engine/deconfliction.ts` — 3D spatial de-confliction using [Turf.js](https://turfjs.org/) (the JS equivalent of Shapely — this stack is Node/TypeScript end-to-end, so no separate Python service): `segmentIntersectsGeofence` does horizontal circle intersection (`turf.booleanIntersects`) *and* an altitude-band overlap check — a real 3D cylinder intersection is always these two checks combined, in any geometry library. `buildDeconflictedRoute` then either climbs over a low-ceiling fence or bends laterally around a tall one (`turf.bearing`/`turf.destination`), and flags any segment that still can't be fully cleared as a `hazard` rather than silently calling it safe. `POST /api/deconfliction/route` exposes it — unit tested in `deconfliction.test.ts` (8 cases: pure intersection logic, overflight vs. lateral choice, and the hazard fallback).
- `client/` — React + TypeScript + MapLibre GL frontend
  - Renders each corridor as a floating 3D ribbon between two "pylons" (fill-extrusion polygons) at the corridor's altitude, colored by battery drain severity
  - Corridor selector (predefined + user-drawn) + live telemetry readout panel with safety warning banners
  - "+ Draw new" lets you click two points on the map to define a corridor, stored in the browser's `localStorage` (`src/customCorridors.ts`) — not synced to the server or other devices
  - "Simulate Flight" generates a guaranteed obstacle course and a fresh gusty wind scenario for every run (`src/syntheticScenario.ts`, seeded per-route so obstacles are reproducible while wind varies each click), reroutes around the obstacles (`src/obstacles.ts` / `src/geo.ts`), and animates a drone through it using the same tested wind-triangle engine — each leg's heading/crab angle comes from a real `POST /api/telemetry/custom` call with that run's synthetic wind. Obstacles actually move during the flight: birds circle their spot, the "other drone" crosses back and forth through the corridor like real crossing traffic, buildings hold still (`animatedObstacleCenter`/`animatedObstacleHeading` in `CorridorMap.tsx`); the reroute geometry itself is still computed against each obstacle's original (unanimated) position
  - Independent of any simulation, 3 background aircraft continuously circle near whichever corridor is loaded (`src/ambientTraffic.ts`, its own always-on animation loop) — ambient "shared airspace" traffic that's there whether or not you ever hit Simulate, distinct from the obstacle-course drone (small planes vs. helicopter)
  - **Air Traffic Control** (`components/AirTrafficControl.tsx`): a live sidebar panel listing each background aircraft's callsign, distance, and bearing from the drone, color-coded clear/advisory/conflict (`computeTrafficStatus` in `src/ambientTraffic.ts`, <50m = conflict, <150m = advisory).
    - **Waze-style live rerouting, not freezing.** An earlier version handled a conflict by freezing the drone in place (subtracting held time out of elapsed) until the intruder's orbit carried it back out of range. That only stopped *our* progress — the orbiting traffic kept moving and could still fly straight through a stationary drone, which is exactly what got reported: a visible mid-air "crash" despite the hold logic technically "working." `CorridorMap.tsx`'s frame loop now continuously sidesteps instead: `evasionTarget` computes a perpendicular offset — away from whichever side the nearest contact is on, growing smoothly as it closes inside the 50m conflict radius and relaxing back to 0 once clear — and a `Rerouting around AT-2 (32 m)` message replaces the old "HOLDING" badge on the map overlay, the sidebar status line, and the ATC panel, plus a pulsing red ring on the traffic marker itself (`.traffic-icon--conflict` in `styles.css`).
    - **A hard, mathematically-guaranteed floor** sits underneath the smooth sidestep and is checked every frame regardless of it: first a relaxation pass pushes away from the centroid of whichever contacts are currently violating the floor (escaping a *single* worst offender, or the raw sum of every violator's push vector, can fail to converge or cancel to ~0 when the drone is boxed in from opposite sides — the centroid avoids that), and anything still violating after that gets an unconditional correction to a point far enough from the centroid of *every* contact that the triangle inequality alone guarantees the floor distance from each one individually, however they're arranged. Verified with a 30,000-trial Monte Carlo stress test reproducing this exact math against up to 10 tightly-clustered contacts (production only ever has 3, far apart) and per-frame drone movement up to 15 m/frame (matching this app's fastest realistic flights).
    - **The floor itself is zoom-aware, not a fixed 10m** (`effectiveDangerRadius` in `CorridorMap.tsx`). The first version used a flat `DANGER_RADIUS_METERS = 10` and still looked like it was hitting planes — because the drone/traffic markers are fixed-*pixel*-size icons (34px/24px), and 10 real meters is only a handful of screen pixels at anything looser than a tight zoom, so the icons visually overlapped well before the real 10m floor was ever actually breached. Measured live rather than assumed: this app's own "overview" camera commonly sits around **zoom 15.4** for these corridors, where 1 pixel is already ~3 real meters — so even the first attempt's 80m visual cap (`MAX_VISUAL_DANGER_RADIUS_METERS`) undershot what the icons needed and still overlapped on screen (confirmed by measuring actual `getBoundingClientRect()` edge-to-edge pixel gaps in a live browser, not just the underlying geo-math). The floor now scales with the map's current meters-per-pixel (`metersPerPixel` in `geo.ts`) so the two icons keep a real on-screen gap at whatever zoom the camera happens to be at, capped at 220m so an extremely zoomed-out view doesn't demand an absurd real-world separation; the evasion trigger radius and max sidestep distance (`EVADE_MAX_OFFSET_METERS`, now 180m) scale up to match, so there's still room for a visible slide instead of the hard floor having to finish the job with an abrupt jump. Re-verified live afterward: 8/8 browser trials with a genuine traffic conflict showed a positive icon-to-icon pixel gap (24-42px while actively rerouting), none negative (overlapping).
  - Camera mode is a **user-selectable toggle** (camera button, top-right of the map), not fixed: **Follow** trails behind and above the drone up close (immersive, banking to face its heading) but a tight zoom generally can't also keep the corridor's endpoints in frame; **Overview** (the default) leaves the camera wherever `frameCorridor` last framed it — both endpoints always visible — and, unlike Follow, leaves manual pan/zoom/rotate enabled during the flight instead of locking them out, since nothing is fighting you for the camera every frame.
  - Playback speed is adjustable (0.25×-2×, `Speed` buttons above the status line) — pick a slower speed to actually watch a reroute or a wind gust play out instead of it flashing by. A single run-to-run wall-clock comparison is a poor way to *verify* this, though — the synthetic wind is re-randomized every click and alone can swing flight duration 10x+, easily swamping the speed setting's effect in any one-off comparison; averaging several trials (or reading the `totalSimSeconds` math directly) is what actually confirms it's working.
  - Banking shows up two ways: the drone icon itself rolls (`setDroneRotation`'s `bankDeg`, up to ±32°, since it's a small icon and can be dramatic) and, more subtly, the whole map canvas tilts a few degrees via a CSS `rotate()` proportional to crab angle (MapLibre's camera has no roll parameter, so this is a fake, capped low so it doesn't fight with tracking the path)
  - A "Satellite" toggle (top-right of the map) swaps between the vector street style and a keyless Esri World Imagery raster basemap — real aerial photography instead of stylized vector tiles. 3D building extrusions only exist in the vector style's own data, so they disappear over satellite imagery (our own corridor/obstacle/drone layers are independent GeoJSON and keep working fine)
  - **"Simulate Emergency TFR"**: spawns a red 3D cylinder (a Temporary Flight Restriction — always tall, 400m ceiling, so it can't just be casually overflown) across the current corridor and sends it to the backend's de-confliction engine. It's now wired into the actual animated flight, not just the overview: an active TFR takes priority over the synthetic obstacle course when you hit "Simulate Flight" — the drone flies the real Turf.js-deconflicted route, and the corridor ribbon fades out in favor of the color-coded path (yellow = rerouted, red = a segment that still can't be fully cleared). Toggling the TFR off restores the normal route and obstacle course.
  - **Emergency failsafe reroute**: after fetching telemetry for whichever planned route is about to fly (direct, obstacle-avoidance, or TFR detour), the app sums `batteryDrainPercent` **across all legs** and aborts before the flight starts — diverting instead to a designated emergency landing zone 70m off to the side — if the cumulative total exceeds 80% (the same reserve threshold used server-side). This is a real pre-flight safety check, not cosmetic: verified directly against the backend with a deliberately saturating crosswind that produces exactly this condition. Earlier this checked each leg's own warnings independently instead of summing them — since each leg's `batteryDrainPercent` is computed as if that leg alone started with a full battery, a single unlucky detour leg (out of the 2-4 a reroute typically has) could look "insufficient" even when the whole trip was well within budget, which was cutting the failsafe in on the majority of runs instead of only genuinely bad ones. **The planned route stays visible when this triggers** — obstacle ribbon, TFR safety-path, whichever was already drawn is deliberately left on the map rather than cleared — and the actual diversion draws as its own distinct orange path (`EMERGENCY_PATH_SOURCE`), so you can see both what was *planned* and what was actually *flown* instead, not just the aftermath. (An emergency landing also used to leave the "Simulate Flight" button permanently disabled — `App.tsx`'s completion check only recognized an "Arrived" status, not "Emergency landing complete", so `simRunning` never reset. Fixed by recognizing both as terminal.)
  - **"Add Refuel Stop"**: click the button, then click anywhere on the map to place a stop — a direct answer to the failsafe above routinely aborting long routes (the TFR detour's "push far out for real visual clearance" fix made detours long enough that the 80%-drain failsafe started tripping on previously-fine corridors). `insertRefuelStop` (`CorridorMap.tsx`) snaps the clicked point onto the nearest leg of whichever route was already planned (direct, obstacle-avoidance, or TFR detour — it runs after all of those, so it doesn't need to know which) and splits that leg into two there, nudged off the leg's own endpoints so both halves are always real legs. Everything downstream already iterated generically over however many legs a path has — the per-leg telemetry fetch, the animated frame loop, the actual-flown trail — so treating the stop as a real intermediate waypoint there means none of it needed special-casing. Two things *do* know about it specifically: the battery failsafe now checks drain **before** and **after** the stop as two independent budgets instead of one cumulative trip (so a route that fails as one long haul can still succeed as two shorter ones), and the frame loop pauses once, briefly (1.4s, fixed, not scaled by playback speed — a lesson learned the first time a hold mechanic existed in this codebase), showing "Recharging at the stop…" when the drone reaches it. Verified live: a corridor+wind combination that reliably tripped the failsafe as a single trip completed normally once split around a mid-route refuel stop, with the recharging pause visibly showing in the status line. Not yet implemented: if one half *alone* is still over budget, this falls back to the same full-abort-to-landing-zone behavior as a flight with no stop at all, rather than flying the good half and diverting only from the stop.

## Quickest way to run it

Double-click **`start.bat`** (Windows) or run **`./start.sh`** (Mac/Linux) in the project root. It checks for Node.js, runs `npm install` automatically if dependencies aren't present yet, starts both servers, and opens `http://localhost:5173` in your browser once it's ready. Close the window (or Ctrl+C) to stop it. Verified end-to-end against a completely fresh copy with no dependencies installed.

## Setup (manual)

```powershell
npm install
```

## Run (dev)

```powershell
npm run dev
```

This starts the API on `http://localhost:4000` and the Vite dev server on `http://localhost:5173` (which proxies `/api/*` to the backend). Open the client URL in a browser.

## Test

```powershell
npm test
```

Runs the telemetry engine's unit tests.

## Notes / assumptions

- **Wind data**: Open-Meteo's forecast API is free and keyless; it only exposes wind at fixed altitude bands (10/80/120/180 m AGL), so the wind service interpolates between the two bands bracketing the corridor's altitude.
- **Crab angle**: standard aviation wind-triangle formula — `WCA = asin((windSpeed/airspeed) * sin(windFromDeg - courseDeg))` — clamped for the (non-physical) case where wind speed exceeds airspeed.
- **Battery drain**: a simplified placeholder power model (`hover baseline + drag·airspeed² + crosswind penalty`), not real airframe telemetry. Swap `DEFAULT_DRONE_PROFILE` in `server/src/types.ts` for real bench-tested coefficients before trusting the numbers.
- **Corridors**: predefined ones are hardcoded (`server/src/data/corridors.ts`); user-drawn ones live only in that browser's `localStorage`. Swapping either for a database is a natural next step.
- **Safety warnings** (`SAFETY_THRESHOLDS` in `server/src/types.ts`):
  - `WIND_SATURATION` (critical) — the crosswind component exceeds the drone's airspeed, so no heading can hold the course at all; it *will* drift outside the corridor.
  - `AGGRESSIVE_CROSSWIND` (warning) — required crab angle exceeds 30°. The wind-triangle math says the corridor can still be held exactly, but a large sustained crab angle leaves little margin for gusts in practice.
  - `BATTERY_INSUFFICIENT` (critical) — estimated drain ≥ 100%; won't reach the destination.
  - `BATTERY_LOW_RESERVE` (warning) — estimated drain leaves less than a 20% reserve on arrival (no margin for diversion or return-to-home).
  - These thresholds are illustrative placeholders, same caveat as the battery model above — tune them once you have real flight-test data.
- **5 obstacle kinds, not 3** (`ObstacleKind` in `client/src/obstacles.ts`): buildings (static), birds (circle a small loop), a generic drone (crosses the corridor back and forth), an emergency helicopter (circles a wider, faster loop — like a medevac/police/news helicopter loitering over a scene — and gets a flashing red/blue "light bar" via CSS on its marker, `.obstacle-icon--emergency` in `styles.css`), and fireworks (stationary, but its rendered radius pulses over time via `animatedObstacleRadius` — a stand-in for successive bursts). All five are seeded per-corridor the same way the original three were, just drawn from a larger kind list (`generateObstacles` in `syntheticScenario.ts`).
  - **Click any obstacle marker for a live info popup** (`obstacleInfoHtml`/`computeObstacleVelocity` in `CorridorMap.tsx`): type, description, size (diameter + vertical extent), current speed, and heading. The speed/heading aren't separately eyeballed guesses — `computeObstacleVelocity` derives them from the *exact same* motion constants driving the on-screen animation (e.g. a bird's speed is literally `radius × angular speed` from the same formula that moves its marker), so the popup always matches what's actually on screen. Buildings and fireworks correctly report "Stationary" with no heading, since neither translates (fireworks pulse in place). A marker's click handler is bound once at creation but reads the obstacle's position/time through a small mutable ref (`obstacleClockRef`) updated every animation frame, so the popup reflects wherever the obstacle actually is *at the moment you click it*, not wherever it was when the flight started.
- **Fixed: the synthetic obstacle course never actually avoided buildings.** `buildRoutePath` (`client/src/obstacles.ts`) detoured laterally around *every* obstacle, including buildings — which are always generated 20-80m taller than the corridor's own altitude (see below), so a "lateral-only" detour left the flight ribbon floating at a fixed altitude that was, by construction, below the very rooftops it was supposedly avoiding. Confirmed live: the actual-flown trail visibly clipped straight through a real downtown high-rise. Fixed by giving buildings the same climb-vs-detour choice the TFR engine already uses (`deconfliction.ts`): a building's required climb (rooftop + 10m clearance) is always comfortably under the 120m "reasonable climb" budget by construction, so buildings now climb over rather than route around, while birds/drones/helicopters/fireworks — which share the flight's own altitude band rather than towering over it — still get the original lateral detour (climbing over a moving bird isn't really avoidance, it's just coincidence). This needed the obstacle-course flight ribbon (`FLIGHT_PATH_SOURCE`) to switch from one fixed layer-wide altitude to per-leg altitude via GeoJSON feature properties (`flightPathFeatureCollection`), the same pattern the TFR safety-path ribbon already used. Verified directly against `buildRoutePath` for all 4 predefined corridors (every one rolled exactly one building this run, every one produced exactly one climbed segment at the correct altitude) and live in the browser (the chase camera shows the ribbon and drone passing visibly above a building's rooftop instead of through it). Known remaining gap: this only fixes the app's own *synthetic* obstacles — the real 3D buildings rendered by the base map style itself (actual OpenStreetMap building data) are still just decoration the app has no hazard model for, so a fixed-altitude corridor through a real downtown can still visually graze real building geometry the synthetic system never knew existed.
- **Fixed: birds/helicopters/drones looked like they weren't moving.** They actually were — confirmed by sampling each marker's real screen position every 400ms — but their circling radius (12-28m) was small enough, combined with this app's typical overview zoom (~15-15.5, where 1 pixel is already 3+ real meters), that the motion only spanned about 8px on screen: technically animating, imperceptibly so. Not a logic bug, a legibility one, same root cause as the earlier traffic-avoidance visual-overlap fix. Bumped the animation radii/amplitude (`BIRD_CIRCLE_RADIUS_M` 12→26, `HELI_CIRCLE_RADIUS_M` 22→42, `DRONE_CROSS_AMPLITUDE_M` 28→48 in `CorridorMap.tsx`) so the sweep reads clearly as motion at that zoom — roughly 2-3x more screen movement, confirmed the same way. These are purely cosmetic constants for the on-screen wobble; each obstacle's actual collision footprint used for route planning (`Obstacle.radiusMeters` in `obstacles.ts`) is untouched, so this doesn't change what the drone avoids or how, only how obviously alive the obstacle looks while it does.
- **Fixed: near-misses with the emergency helicopter obstacle.** This was a direct consequence of the previous fix above — bumping the animation radii for visibility (12→26m bird, 22→42m helicopter, 28→48m drone) made the on-screen wobble bigger, but `buildRoutePath`'s lateral clearance distance was still only `radius + corridor half-width + margin`, unchanged from before: it had no idea the obstacle could now wander up to 42m from its own centroid, so a "cleared" route could pass right through where a circling helicopter or crossing drone actually travels. Fixed two ways: (1) the clearance calculation now adds each kind's actual wobble radius, using the *same* constants as the animation (moved to `obstacles.ts` as the single source of truth, imported by `CorridorMap.tsx`, specifically so the two can't drift apart silently like this again), and (2) the helicopter — the one kind explicitly meant to read as an emergency vehicle — gets an additional 45m on top of that, so a near-miss with it in particular reads as deliberately wide rather than merely adequate. Verified directly with a standalone script calling `buildRoutePath` against three obstacles of equal base radius: waypoint clearance from the centroid comes out to 73m for a bird, 95m for a crossing drone, and 134m for the helicopter — not just eyeballed — and confirmed live in the browser as a clearly wide swing around a helicopter obstacle.
- **Fixed: obstacle-course route could visually overlap the drone despite being geometrically safe.** Three distinct bugs stacked up to produce this, found by iterating through live verification rather than guessing: (1) `effectiveDangerRadius`'s flat nadir (top-down) `metersPerPixel` approximation was being read off `map.getZoom()` at the moment "Simulate Flight" was clicked — if that happened before `frameCorridor`'s 800ms fitBounds animation had settled (easy to do, confirmed live), the zoom was still mid-transition from whichever corridor was previously framed, silently baking a wrong clearance into the entire flight. Fixed with `overviewTargetZoom`, which computes the *actual* settling zoom synchronously via `map.cameraForBounds()` instead of trusting the live camera. (2) Even with the correct zoom, flat `metersPerPixel` is still only a top-down approximation — this camera is pitched 55-64°, under which real screen distance per meter varies continuously across the scene (perspective, not a uniform ratio), so a position farther into the pitched view needs more real-world clearance than one nearer the camera to read the same number of pixels apart. A scalar fudge factor on top of the nadir estimate (tried 1.4×, 1.8×, 2.2×) kept narrowing the gap empirically but never reliably eliminated it, because the correction actually needed depends on *where* the obstacle sits in the scene. (3) The fix: `buildVisuallyClearRoute` builds a candidate route, then verifies it against the map's *real* projection (`map.project()`) rather than any approximation — sampling points along every leg, measuring actual on-screen distance to each obstacle (including its animated wobble, itself converted to local pixels via projection rather than assumed), and progressively widening the route only if the real gap comes up short. Verified with 10 live trials after the fix: 10/10 passed with 32-93px of real margin, fully deterministic (same corridor reliably reproduces the same clearance), versus roughly 50% failure rates — including some down to -29px, i.e. genuinely overlapping — at every stage of the flat-approximation approach before it. A drone marker visually close to a building specifically is expected, not a bug: buildings are climbed over (see below), and MapLibre markers are ground-anchored only, so the marker itself can't visually show the altitude gain no matter how high the flight ribbon actually renders.
- **Fixed: the TFR detour could visually overlap the restricted zone it was supposedly avoiding.** Same root cause family as the obstacle-course fix above (a server-computed route, certified clear by real-world meters, with no idea what the client's camera is doing), but needed two further rounds of live-verified fixing to fully close: (1) `widenTfrRouteForVisualClearance` mirrors `buildVisuallyClearRoute`, pushing the detour waypoint further from the fence using the map's real `map.project()` distances — but the first version checked clearance only *at the waypoint itself*, the same single-point mistake already made (and already fixed) once for the obstacle course; a route could read as clear there while the straight segments leading to and from it still cut through the fence (confirmed live: up to -21px, a real overlap). Fixed by sampling the whole path, not just the waypoint. (2) Even then, occasional small overlaps (down to -3px) persisted on the shortest corridor — because `spawnEmergencyTFR` placed the fence anywhere from 40-60% along the route with no awareness of the corridor's actual length, a short corridor could put the fence close enough to a *fixed* endpoint (the start/end point itself, which no detour waypoint can move) that the segment connecting to it had no room to clear, no matter how the detour was shaped elsewhere. Fixed at the source: `spawnEmergencyTFR` now keeps the fence at least `radius + 150m` from both endpoints, computed from the corridor's real length rather than a fixed fraction. Verified with 25 live trials across all 4 corridors after both fixes (12 on the shortest/hardest one specifically): 23/23 completed runs passed with real projected clearance of 11-118px; the 2 that didn't complete were unrelated browser/network timeouts from running many Playwright instances back to back, not app failures.
- **Obstacles never spawn near either endpoint.** `generateObstacles` (`syntheticScenario.ts`) already spread obstacles along `t ∈ [0.2, 0.8]` of the corridor's length, but that's a *fraction* — for a short corridor, or for a wobbly kind (a circling helicopter or crossing drone can wander tens of meters from its own centroid), 20% of the way in can still land close enough that the obstacle's rendered footprint or animated swing reaches the start/end marker. Fixed with a hard, kind-aware minimum: each obstacle's along-path position is now clamped to stay at least `70m + its animated wobble radius + its own footprint radius` from both ends (capped at 40% of the corridor's length so a very short corridor can't invert the bounds). Verified directly (not just eyeballed) with a script computing worst-case clearance — obstacle footprint radius subtracted from wobble-adjusted distance — for all 4 predefined corridors (all comfortably clear) and a range of synthetic corridor lengths down to 150m (all clear, 14-40m+ margin). An 80m corridor — shorter than a football field, well below any real corridor in this app — can still fail this in the pathological case of a big-wobble kind landing right at the edge of its allowed range; not chasing that further since nothing in the app actually produces a corridor that short.
- **Obstacles are synthetic, deliberately** — an earlier version queried the map's real rendered building tiles, but that only produced obstacles where OpenStreetMap happens to have tall buildings, so most routes (or any user-drawn one) showed "airspace clear." `src/syntheticScenario.ts` instead procedurally generates 2-4 obstacles (buildings, birds, or other drones) along *any* two points — a shuffled kind sequence guarantees a mix of all three when there are 3+, rather than occasionally landing on all-buildings by chance — seeded by the corridor's id/coordinates so re-simulating the same route gives the same course, while a different route gets a different one. Buildings are always taller than the corridor's altitude and birds/drones are always "active" — every simulation guarantees a reroute.
- **Wind is synthetic too, for the simulation specifically** — each "Simulate Flight" click generates a fresh 6-15 m/s gust from a random direction (`generateSimulatedWind`) and sends it to the backend as an explicit override (`POST /api/telemetry/custom` body's `wind` field, see `parseWindOverride` in `server/src/routes/telemetry.ts`), so the crab-angle/reroute/banking demo doesn't depend on however calm it actually is outside right now. The static **Telemetry** panel (before you hit simulate) is unaffected and still shows real live Open-Meteo wind for the selected corridor. (The range was originally 7-19 m/s; that made full wind-speed saturation — and therefore the emergency failsafe landing — trigger on roughly half of all simulated flights, cutting the reroute/obstacle/traffic-hold demo short more often than not. 6-15 m/s still forces a clearly visible crab angle almost every run while making saturation an occasional event instead of a coin flip.)
- **Reroute geometry**: a simple lateral detour around each obstacle's clearance circle (radius + corridor half-width + margin), not a real path planner — it doesn't check whether a detour point clips a *different* obstacle.
- **Simulation timing**: a 5-15s base duration (scaled from each leg's real ETA) is further divided by the selected playback speed (0.25×-2×) and capped at 60s total, so relative pacing between windy/calm legs is preserved but the absolute duration isn't realistic. A wind strong enough to fully saturate a leg (crosswind ≥ airspeed) can make that leg's ETA balloon before compression — you may see the drone crawl through one leg and zip through others, which is the `WIND_SATURATION` case rendered visually rather than a bug.
- **Satellite basemap**: Esri's World Imagery tile service, used the same way most open-source map projects use it (no key, standard attribution). It's a different tile provider than OpenFreeMap's vector tiles, so don't expect pixel-identical coverage/freshness between the two views.
- **Known cosmetic issue, unrelated to any of the above**: a handful of POI icons in the base "liberty" vector style occasionally fail to load their sprite image, and MapLibre falls back to a red placeholder shape — visible even with no corridor selected or simulation run. It's a pre-existing quirk of that map style's sprite sheet, not the obstacle/traffic system; confirmed by inspecting the map's actual layer sources directly (obstacle/flight-path sources are genuinely empty when this shows up).
- **Visual design**: Inter (UI) + JetBrains Mono (telemetry/callsigns/numbers) loaded from Google Fonts in `index.html`; the whole sidebar uses a consistent card system (`--panel`/`--border`/`--radius-*`/`--shadow-card` tokens in `styles.css`) rather than one-off styling per component.
- **Fixed: the actual-flown trail exposed a real erratic-path bug, not just a rendering one.** "Lowry Park Traverse not reaching destination" turned out to be true in spirit but not literally — every automated trial (20+, across speeds/wind/TFR combinations) did eventually reach "Arrived." What the actual-flown trail (below) revealed live was *why it looked broken*: the drone's real path was a wild, multi-turn zigzag ranging hundreds of meters outside the corridor before snapping back to arrive, not the clean sidestep the rerouting system was supposed to produce. Root cause: `evasionTarget`'s side-to-evade (`side = relative >= 0 ? -1 : 1`) was recomputed fresh from whichever traffic contact was nearest *every single frame*. With 3 independently-orbiting aircraft and a conflict radius wide enough to avoid visual overlap at a zoomed-out view (see the zoom-aware floor above — up to 300m+), which contact counts as "nearest" can swap between drones frame to frame, and the same drone's relative bearing can cross past the heading line as it circles — either one flips the chosen side, and at `EVADE_MAX_OFFSET_METERS` this large, a flip mid-slide is a large excursion in a new direction, compounding into a jagged path over a multi-second episode. Fixed by making the side *sticky*: `evadeSide` is chosen once when an evasion episode starts and held for its entire duration (magnitude still reacts live to the current nearest threat's distance), only releasing back to "free to choose" once the *smoothed* offset has fully relaxed to ~0 — not just whenever the raw target momentarily reads no-conflict, which could otherwise re-lock a flipped direction mid-slide. Confirmed live: the same TFR/traffic scenario that previously produced a 4-5-turn zigzag now produces a single smooth bulge around the conflict.
- **Actual-flown trail** (`ACTUAL_PATH_SOURCE` in `CorridorMap.tsx`): a thin bright-pink ribbon laid down live, frame by frame, as the drone actually moves — distinct from the wider planned-route ribbons (cyan obstacle-avoidance, amber/red TFR safety-path, orange emergency diversion), which are all computed once before the drone starts moving and never change afterward. Before this existed, a live ambient-traffic sidestep (see the rerouting system above) had nothing recording it anywhere once the moment passed — the drone marker would visibly drift off the pre-drawn planned path mid-flight with no trace of why. Points are appended only once the drone has moved ≥3m from the last recorded point (keeps a long flight's polyline reasonably sized) and the whole trail persists after arrival, so it doubles as a post-flight record of exactly what was flown, not just what was planned. Floated 35m above the corridor's own altitude band (which the planned ribbons occupy within ±3-4m) rather than at the same height — the common case is the actual path coinciding almost exactly with the plan, and at the same altitude this thinner ribbon would render completely hidden inside the wider planned one instead of reading as its own visible layer. Confirmed live: a genuine traffic-avoidance sidestep shows the pink trail visibly bending away from the cyan/amber planned path while the status line reads "Rerouting around AT-2," then the two lines converge again once clear.
- **Fixed: TFR detour looked like it flew straight over/through the cylinder.** The lateral-detour math (`server/src/engine/deconfliction.ts`) was correct — a real ~130-190m sideways clearance — but two things hid it visually: (1) `CLEARANCE_MARGIN_METERS` was a fixed 40m, tiny next to the TFR's 90-150m radius, so the detour hugged the fence's edge; now `Math.max(120, radius * 0.75)`, roughly doubling-to-tripling the visible gap. (2) The bigger cause: the "overview" camera (`frameCorridor` in `client/src/components/CorridorMap.tsx`) framed every corridor at a **fixed** `bearing: -20`, so for a corridor running in some other direction (e.g. the downtown NE-running one), the perpendicular detour offset pointed mostly *into the screen* under the pitched 3D camera and got foreshortened by perspective until it was visually indistinguishable from a straight line through the fence. Fixed by locking the overview bearing to the corridor's own course (`bearing: bearingDeg(corridor.start, corridor.end)`), so the flight always runs "up the screen" and any lateral bend reads as unambiguous left-right movement. Confirmed live: same fence/segments, before/after screenshots go from "path looks straight through a red tower" to "path visibly bends left around it, rejoins near the end marker." The chase/follow camera was never affected — it already sets bearing to the drone's live heading every frame.
